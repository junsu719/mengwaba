# 悶蛙吧 CIS Redesign — 補充規格(與原規格一併執行)

原規格(MENGWABA CIS + UI/UX Redesign Specification)整體可行,以下為**必須一併遵守的補充條款**。衝突時,以本文件為準。

---

## A. 最重要:設計必須涵蓋四個城市,不是只有高雄

原規格的範例網址是高雄頁面,但本站有四個城市、**四種不同的資料形狀**:

| 城市 | depart(離站時間) | 星期 | 特殊 |
|---|---|---|---|
| 高雄 | 有(`21:24~21:27`) | 完整 | — |
| 台中 | 有 | 完整 | 有**沿街收運**(措辭不同,不是「停靠」而是「經過」) |
| 桃園 | **一律無** | **約 70% 未知** | 需顯示免責說明 |
| 新北 | **一律無** | 完整 | **有廚餘班表**(第三種收運類型) |

因此:

1. **Hero 的時間顯示不可寫死成 `21:24 ~ 21:27` 區間格式。** 沒有 depart 時只顯示單一到站時間(現有措辭:「約 21:24 抵達」)。**嚴禁用 arrive + N 分鐘推算出一個 depart。**
2. **週表(§19)的七天 ● / — 呈現,在星期未知的點必須整個不渲染**,改顯示現有的免責說明:
   > 本站僅取得此清運點的到點時間,未取得收運星期。完整班表請以桃園市環境管理處「垃圾清運路線即時查詢系統」為準。
3. **新北的廚餘區塊(`foodscraps_schedule`)必須納入設計**,比照資源回收區塊,用 `hasFoodscraps` 判斷是否渲染。原規格完全沒提到這塊。
4. **純資源回收點**(無一般垃圾班次)不可顯示「今天沒有收運」——那是錯誤結論。沿用現有分支措辭。
5. **台中沿街收運**的措辭邏輯(`isPassThrough`)不可被重寫覆蓋。

**驗收要求**:設計完成後,四個城市各至少實際渲染 3 頁檢查,並涵蓋:有/無 depart、星期已知/未知、有/無資源回收、有/無廚餘、沿街/定點、純回收點。

## B. 「距離現在約 XX 分鐘」的實作限制

原規格 §17/§18 提到倒數,並警告不要做錯誤的時間計算。技術上必須:

1. **一律前端計算(client-side JS)**。頁面經 Cloudflare 邊緣快取,伺服器端算出的倒數對看到快取版本的使用者是錯的。
2. **時區強制 `Asia/Taipei`**,不可依賴執行環境時區(Workers 在資料中心)。
3. **僅在該點的星期與時間皆已知時顯示**。桃園星期未知的點**不得顯示倒數**——不知道今天收不收,就無從倒數。
4. JS 失效時不可留下空白或 `NaN`,預設不渲染該區塊。

## C. 不得刪除既有 SEO 內容(內容退化是最大風險)

2026-08-09 已上線的行政區頁強化內容,**必須全部保留**,只可重新排版,不可為了視覺清爽刪除:

- 里別索引(含錨點跳轉)
- 依里別分組的清運點列表
- 星期分佈總覽
- 時段分佈
- 資源回收 / 廚餘覆蓋率
- 資料驅動 FAQ
- 資料來源與更新日期
- 站內連結(同縣市其他行政區、城市索引)

另外:

- **`title` 與 `meta description` 不可改動**,除非先跟 Jun 確認。現行版本是依 GSC 真實查詢字優化過的(包含「時間表」這類用字),改動會直接影響排名與點閱率。
- **品牌名不可放在 title 最前面**。使用者搜的是「仁武垃圾車時間表」,不是品牌名。

## D. 資料來源標註是授權義務,不是裝飾

四個城市的資料皆依「政府資料開放授權條款第 1 版」提供,**該條款要求標示出處**。資料來源區塊與 `fetched_at` 更新日期**不得因版面調整而移除或縮到看不見**。

## E. 效能:字型是最大風險

原規格 §27 要求 Performance > Visual effects,但 §5 指定 Noto Sans TC ——完整字重檔案極大,直接載入會嚴重傷害 LCP。必須:

- 字型子集化(只含實際用到的字),或
- 使用 `font-display: swap` + 系統字型 fallback,或
- 評估直接用系統中文字型堆疊

**部署前後各量一次 Lighthouse 分數,不得低於現況。**

## F. 不得新增任何網址

原規格 §26 已說不改網址,再明確一次:

- **不得新增頁面**(包含「即將推出」的工具頁、分類頁、路名頁)。目前 73,257 個網址處於「已找到-目前尚未建立索引」,Googlebot 一天只來 12 次,新增網址只會讓比例更難看。
- 首頁的「即將推出」工具卡片**只能是無連結的視覺元素**,不可連到任何實際頁面。
- 全站搜尋若後端尚未支援,**只做 UI 不做假功能**(原規格 §25 已載明)。

## G. 保留既有的 404 頁

站上已有客製 404 頁(標題「找不到這個清運點」+ 搜尋框 + 該行政區清運點列表連結 + 四縣市索引)。**必須保留其功能與 HTTP 404 狀態碼**,僅可套用新視覺。

## H. 吉祥物:以文字規格為準,不以示意圖為準

附圖的首頁示意出現大面積卡通青蛙,與原規格 §6「不要可愛幼兒園風格」、§7「極簡、幾何、小尺寸、不要大面積卡通插畫」互相矛盾。**以文字規格為準**,蛙蛙僅出現在 loading / empty / error / 資料更新等小尺寸情境。

## I. 驗證與上線流程(沿用既有鐵律)

1. 現有 **49 個 snapshot 測試**必涵蓋文案輸出。改動若使測試失敗,**不可盲目更新 snapshot** —— 必須先確認新輸出正確、並由 Jun 讀過才更新。
2. 組合矩陣重跑:四城市 × 各資料形狀,實際輸出字串貼給 Jun 讀過。
3. `npm run build` 通過。
4. commit → **`wrangler versions upload`** 產生版本專屬預覽 → 回報預覽網址,**停下等 Jun 人工抽看** → 經 Jun 明確同意才 `wrangler versions deploy`,部署前記錄回滾版本 ID。
5. **`wrangler d1` 指令一律在 `site/` 目錄執行**(repo 根目錄的 `.env` 會讓 wrangler 誤用無 D1 權限的 token)。

## J. 分階段執行,不要一次做完

建議順序(每階段回報再往下):

1. **Phase 1 Audit**(原規格 §35)—— 只讀不改,回報現有架構與風險
2. **Phase 2 Design Tokens** —— 純 CSS 變數,零風險
3. **Phase 3 Core Components** —— 元件庫,尚未套用
4. **Phase 4 首頁** —— 首頁不是流量來源,風險最低,可先驗證整套視覺
5. **Phase 5 行政區頁 + 清運點頁** —— **風險最高,四城市邊界情況全部要驗**
6. **Phase 6 Responsive QA + Lighthouse**

**Phase 4 之後先停下讓 Jun 看過,再進 Phase 5。**
