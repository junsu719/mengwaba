# 悶蛙吧 MengWaBa

台灣生活工具站 — 目前提供全台四縣市垃圾車清運時間查詢,以及政府行政機關辦公日曆表 / 連假查詢。

🔗 **[mengwaba.com](https://mengwaba.com)**

---

## 這是什麼

一個 pSEO(programmatic SEO)工具站,把分散在各縣市政府、格式互不相同的開放資料,整理成結構化、可查詢的網頁。

目前上線的工具:

- **垃圾車清運時間查詢**:高雄、台中、桃園、新北,共約 **73,000+ 個清運點**,每個清運點一個獨立頁面,涵蓋一般垃圾、資源回收、廚餘三種收運時刻。範例:[高雄市左營區垃圾車時間](https://mengwaba.com/trash/kaohsiung/zuoying/)
- **行事曆 / 連假查詢**:2026、2027 年政府行政機關辦公日曆表,含拼假攻略計算機、`.ics` 行事曆下載

## 資料來源

每個縣市的資料來源、取得方式、格式都不一樣,這也是這個專案最花時間的部分:

| 縣市 | 來源 | 格式 |
|---|---|---|
| 高雄市 | 高雄市政府環境保護局官方 PDF 班表(kepbgps.kcg.gov.tw) | PDF,人工季度下載(robots.txt 禁止自動存取) |
| 台中市 | 開放資料 CSV/API | CSV |
| 桃園市 | 官方即時查詢系統(route.tyoem.gov.tw),逆向工程其查詢端點 | JSON(非公開 API) |
| 新北市 | 新北市資料開放平臺 | JSON/CSV/XML |
| 行事曆 | 行政院人事行政總處官方日曆表 | CSV,人工下載(robots.txt 禁止自動存取) |

授權皆為「政府資料開放授權條款第 1 版」,允許商業加值利用,須標示出處(各頁面內皆有標註)。

## 架構

- **前端**:[Astro](https://astro.build),Cloudflare Workers 部署
- **資料庫**:Cloudflare D1(SQLite),僅用於高流量、無法預先產生的清運點頁(約 73,000 頁)
- **靜態預先產生**:首頁、城市索引頁、行政區頁(約 130 頁)、行事曆全部工具 —— 只要頁面數量可控、資料非高頻更新,一律靜態化,零資料庫查詢
- **ID 設計**:清運點網址採內容雜湊(sha256 前 10 碼十六進位),搭配 git 版控的消歧對照表,確保資料來源改版時網址不受影響
- **自動化**:各縣市資料每季手動重新抓取、正規化、驗證(L1/L2/L3 三層驗證)、匯入 D1

## 一些踩過的坑

**2026-07-22:改一個 ID 方案,弄丟三週的搜尋排名。** 把清運點的網址識別碼從全域流水號改成內容雜湊,是為了讓網址在資料來源改版時保持穩定——但沒有想到這個改動本身讓所有「已經被 Google 索引」的舊網址一夜之間全部 404。曝光數從單日 600+ 直接歸零,靠事後重建 301 對照表才逐步救回。教訓:**改變 ID 方案時,不能只驗證內部消費端,還要考慮外部(搜尋引擎、書籤)對舊 ID 的既有引用。**

**D1 免費方案額度:從超標 409% 降到 47%,而且不用改架構,只是找出真正的浪費在哪。** 一度診斷「缺索引」,結果發現索引其實都正確使用,問題是「查詢天生要讀整個範圍」這個設計本身——某個查詢的 `queryEfficiency` 高達 0.999(索引完美),但依然是全站最大宗的讀取來源,因為它每次都讀進一整個行政區的資料只為了顯示 6 筆。真正的解法不是加更多索引,是把只有 130 頁、一季更新一次的行政區頁改回**完全靜態預先產生**,D1 讀取直接歸零。教訓:**「索引有被使用」不等於「查詢有效率」。**

**pSEO 在新網域上的真實限制:Google 願意爬,但不見得願意收。** 一個站發布七萬多個結構高度相似的頁面,即使全部語法正確、資料真實,Google 對新網域的索引預算仍然有限——目前僅約 4% 的清運點頁被索引,行政區層級(較少、內容較豐富)的索引狀況明顯較好。這推動了往後的策略:優先做頁數少、可預先產生、且更容易被外部連結的工具(如行事曆),而不是持續堆疊更多長尾頁面。
